# Cocktail architecture and decisions

How the system fits together and why. Plan and requirements are in
[`docs/QUEST_PRD.txt`](docs/QUEST_PRD.txt), live progress in [`docs/STATUS.md`](docs/STATUS.md),
and setup in [`README.md`](README.md).

The proposed recorded-scene expansion is specified in
[`docs/AV_SOUND_DISCOVERY_SPEC.md`](docs/AV_SOUND_DISCOVERY_SPEC.md): autonomous sound
and speaker discovery, instance association, prompted stems, and synchronized mask
highlighting. It maps to the existing hub modules and distinguishes verified model
contracts from planned implementation; it does not change the current live defaults.

Each decision has a status:

- **Merged**: in `main` and working (evidence label given).
- **Proposed**: in an open PR, or recommended from measurements but not built yet.
- **Open**: not decided.

Evidence labels follow the team convention: hardware-tested, mocked, replayed, simulated,
untested. Last updated 2026-10-25 (after PRs #37-#51). Anything about direction accuracy is
simulated unless it says "real 3S".

## System overview

```
 Quest 3S (Unity, thin client)                   Laptop hub (Python 3.12, RTX 5070 Ti Laptop 12 GB)
 ─────────────────────────────                   ─────────────────────────────────────────────────
 mic audio  ── /ingest/audio (binary) ──────────▶ ingest ─▶ 10 s audio ring (16 kHz, headset clock)
 camera JPEG ─ /ingest/video (binary) ──────────▶ ingest ─▶ newest frame only ─▶ vision (SAM 3)  [C5]
 head pose,  ─ /ingest/pose  (JSON)  ───────────▶ ingest ─▶ 10 s pose buffer (yaw, pitch)
 input                                                         │
                                                               ▼
                                                 separate: 2 voices + residual, labels   [C3]
                                                               │ per-mic band levels
                                                               ▼
                                                 locate: bearing from head movement      [C4]
                                                               │ GET /sources (slots s1, s2, ...)
                                                               ▼
                                                 track: stable ids t1, t2, ... (runs inside events)  [D1]
                                                               │
 labels, arrows ◀── /events (JSON, every 100 ms) ◀──── events: tracker + /tracks              [D1, #37]
 3D playback    ◀── /audio/out (binary, 48 kHz)    ◀──── out: chosen voice + room                [M2, #42]
 select / stop  ── InputEvent on /ingest/pose ────▶ events/selection: choice = a tracker id
```

The mock headset (`hub/mockclient`) replaces the left column for testing without a headset.
The Quest side (left column) is merged (PRs #18, #28, #38) and hardware-tested for streaming.
The whole hub loop is now merged and runs on simulated and replayed sessions: the tracker sits
after `LiveLocator` inside `hub/events` and feeds `/events`; `hub/out` sends the chosen voice back.
What has **not** been done: the chosen-voice audio heard on the headset, camera outlines (SAM 3,
C5), and any of it on real 3S recordings.

## Decisions

### D1. The laptop hub does all processing; the headset is a thin client
**Merged** (PRD). The Quest streams sensors and renders results. Models run on the laptop GPU.
- **Why:** the models (separation, SAM 3, SAM Audio) need a desktop-class GPU; the headset
  can't run them.
- **Cost:** network delay and jitter. Mitigations: separate channels, small buffers, USB or a
  private hotspot.

### D2. Hub stack: Python 3.12, one uv project in `hub/`, one folder per task
**Merged** (PRs #10, #15, #11, #21, #30, #37, #42, #46-#51). Packages: `protocol/` (A2),
`ingest/` (B3), `mockclient/` (B4), `separate/` (A6/C3), `locate/` (A8/C4), `track/` (D1),
`events/` (live tracker and `/events`), `out/` (`/audio/out`). Early phases without models:
`vision/` (mask store), `who/` (audio-visual matcher), `replay/` (residual math), `render/`
(viewer bundle) and `av_scene/` (D17). The separation benchmark harness from PR #20 and the
real-data tools (D16) live in `eval/`, the former with its own `bench` dependency group.
- **Why:** the ML ecosystem is Python. One project with one lockfile avoids version drift.
  One owner per folder keeps parallel work from conflicting (PRD section 14).
- **GPU dependencies are an opt-in group** (`uv sync --group gpu`): PyTorch built for CUDA
  12.8, ClearVoice, transformers. That way the 8 GB dev laptop and CPU-only machines aren't
  forced to install them.

### D3. Wire protocol: WebSockets, separate channels, frozen schema
**Merged** (PR #10, A2; C# generated by `python -m protocol.export`).
- **Separate sockets** for audio, video, pose/input, events and audio-out, so a large video
  frame never delays audio.
- **Binary framing:** 4-byte header length, JSON header, then the raw payload.
- **Every client message carries `seq`, `device_ts_us` (headset clock) and `epoch`** (which
  increments on reconnect).
- **The schema is frozen:** changes only by team agreement.
- **Audio chunk timestamp = capture time of the chunk's first sample.** The hub assumed this
  (PR #15) and the Quest client sets it this way (PR #18, `MicStreamer.cs`).
- **The Quest 3S delivers 2 raw mic channels at 48 kHz** (PR #18, hardware-tested: native
  `AudioRecord` UNPROCESSED, Unity Microphone as fallback). Channel order (left/right) is still
  unconfirmed; it matters for D8.

### D4. One clock: the headset's; audio converted to 16 kHz at ingest
**Merged** (PR #15, simulated).
- **All hub data is indexed by `device_ts_us`.** Audio and head pose line up without
  converting between clocks.
- **Audio is resampled to 16 kHz at ingest,** since the models run at 16 kHz. The resampler
  keeps its state between chunks, so chunk boundaries add no artifacts.
- **Its 12-sample (0.75 ms) lag is subtracted from the buffer timestamps.** Without that
  correction, separation scoring was off by 25 dB (found and fixed in PR #19).

### D5. Rolling buffers: 10 s of audio and pose, only the newest video frame
**Merged** (PR #15, simulated).
- **Why 10 s:** enough for 2 s separation windows and the 5 s replay (D3 task), and the PRD's
  privacy rule ("live buffer only, 10 s").
- **Video keeps only the latest frame.** SAM 3 is slower than the camera, so older frames are
  dropped and counted, never queued.
- **Gaps up to 2 s are filled with silence** so timing stays correct. A reconnect, a clock
  jump or a longer gap resets the buffers.
- **Malformed messages are counted and dropped,** never allowed to close the connection.

### D6. GPU budget: 12 GB, not 16 GB
**Merged** (PRs #13, #24; hardware-tested). The live machine's RTX 5070 Ti **Laptop** GPU has
12 GB (11.9 GiB usable). It's Blackwell, so it needs PyTorch built for CUDA 12.8 or newer.

| Model | Use | GPU memory | Speed |
|---|---|---|---|
| MossFormer2 + AST labels | live separation (C3) | ~1.1 GB | ~460 ms per 1 s hop |
| SAM 3 image model | outlines (C5) | ~4.0 GB | ~320 ms per frame + ~80 ms per prompt |
| SAM Audio small-tv, core parts only | replay (D3 task) | ~4.4 GB peak | ~2.1 s per 5 s clip per sound |
| Gemma 4 E2B, 4-bit | later | 2.9 GB + KV cache (official table) | not measured |

- **The first three fit together: about 9.5 GB.**
- **SAM Audio fully loaded takes 22.3 GB.** Only its core parts may go on the GPU (D10).
- **Full-precision Gemma, SAM Audio base/large, and the SAM 3.1 tracker don't fit or don't work** (D9).

### D7. Live separation: MossFormer2 on sliding windows, the residual is "everything else"
**Merged** (PR #19, A6/C3; hardware-tested on simulated audio).
- **How it works:**
  - MossFormer2_SS_16K (Apache-2.0) splits two voices from 2 s windows every 1 s.
  - Overlapping halves are cross-faded, and voice order is kept by matching the overlap.
  - Stream 3 is the mix minus the two voices: music and other sounds.
- **Labels:** AST (AudioSet, 527 classes) labels each stream, mapped to speech / music /
  alarm / siren / other and smoothed across hops.
- **Results:**
  - **+17.8 / +17.1 / +17.5 dB** on a simulated 2 talkers + music scene; the target was +8 dB.
  - Labels correct.
  - A listening check confirmed the voices are well separated.
- **Why MossFormer2:** best measured quality of the candidates. Waveformer has no speech or
  general music class; GTCRN only enhances speech. It's fast enough for 1 s hops on this GPU.
- **One talker, or none:** MossFormer2 always outputs two voices, so with a single talker it
  splits that person across both voice streams. Two gates fix this (PR #26):
  - **Direction gate:** if the two voice streams arrive from the same direction (their
    left/right level differences differ by less than 4.5 dB), they're one source and are
    merged. Compared **per band** (1–2, 2–4, 4–8 kHz, PR #21): head shadow depends on
    frequency, and the separator gives the two halves of one talker different frequency
    regions, so a single broadband comparison made them look like two directions.
  - **Speech gate:** a voice stream that doesn't sound like speech moves into the residual.
- **Why direction for one-talker merging:** level correlation and short-window voice fingerprints
  (WavLM speaker embeddings) could not distinguish one split talker from two real ones, including
  a same-gender pair. Speaker embeddings are not used to make that merge decision.
- **Optional voice-slot memory:** the live separator can maintain WavLM speaker profiles from
  accumulated active speech and consult them when an output returns after a pause. It remaps only
  above similarity and margin thresholds; otherwise it preserves the overlap ordering. This is a
  slot-continuity aid, not a claim that the separator has fully solved speaker tracking. The
  checkpoint's license scope is unclear (see the model card), so it is not redistributed.
- **Direction memory remains outside the separator.** Head-relative directions drift as the head
  turns, so a direction memory inside the separator made single talkers hop between streams.
- **Scenario suite** (`python -m separate.suite`, 11 simulated scenes):
  - two talkers, including two men and music louder than the speech: +17 to +22 dB;
  - one talker: +9 to +16 dB in a single stream;
  - three voices: the third ends up in the residual.
- **3+ voices: parked (PR #27, draft).** Order matching across all streams, a gated second pass
  on the residual and 4 s windows reach +18.5 / +11.3 / +13.3 dB with three talkers (vs +7 /
  +6 / +1 today) and run in real time in bf16. Not merged by decision; pick it up from the PR.
- **Limits:**
  - About 1–2 s of delay: fine for labeling and locating, too slow for live listening.
  - At most 2 voices, plus 1 residual.
  - Two talkers standing in the same direction get merged.
  - The 4.5 dB threshold is tuned for ear-level mics and needs re-tuning on the 3S.
  - Clean read speech in the tests, so expect lower scores on real room audio.

### D8. Locating: bearing from natural head movement, using per-mic levels of each stream
**Merged** (PR #11 A8 estimator, by Lalitha; PR #21 C4 wiring; simulated).
- **Inputs:** separation produces each stream as heard at each mic (spectrogram masks applied
  to every mic). It then computes band levels at 20 Hz in the estimator's 5 bands
  (500 Hz – 8 kHz).
- **Processing:** the estimator matches how those levels change as the head turns, giving a
  360° bearing in the world frame. Convention: 0 = initial forward, + = right.
- **Bearings are withheld until the estimator has seen enough head movement.**
- **Output** (`LiveLocator`, served at `GET /sources`): one protocol `Source` per separator slot
  with label, world bearing and confidence, and a state: `tracking` while heard, `last_seen`
  after 2 s of silence, `lost` after 10 s. Never-heard slots aren't published; ambiguous
  (mirror) bearings are capped at 0.5 confidence.
- **`source_id` is a separator slot (`s1`, `s2`, ...), not a person.** Slots change occupant;
  identity is D1's job (D14).
- **World 0°** is the headset's tracking-space forward, which equals "initial forward" only if
  the tracking origin faced forward. Needs a headset check (recentring shifts it).
- **Simulated errors:** female voice within 7–16°, music 5–15°, **male voices pulled 30–45°
  toward the front** whichever side they're on (swapping sides showed the error follows the
  voice, not the side, so it's not a wiring bug). The estimator also reports full confidence
  when wrong. Findings are on PR #11.
- **Real-world test tooling** (PR #32, Lalitha's from #29): `quest/tools/run_locate_take.ps1`
  records a take on the 3S with a sound source at a known angle and scores it with
  `locate.real_eval`. The recorder is hardware-tested.
- **Real 3S results (2026-10-24, 10 labeled takes with a laptop noise source):**
  - **The level (head-shadow) method fails on the 3S:** 59–180° off on valid takes, often
    "locked" at 90%+ confidence. The two raw mics are ~0.5–1 cm apart (2-sample lag,
    correlation ~0.93), so they share almost the same level, and the loudness-vs-yaw swing is
    only a few dB.
  - **Most early takes were invalid, not locator failures:** the test noise never played (a
    launch issue), or there was no head motion. `real_eval` now marks those INVALID (PR #34).
- **Experimental 3S mode: inter-mic delay + head yaw** (`locate/pair.py`). The delay between
  the two mics traces a sinusoid as the head turns; its phase gives the bearing. Device
  constants (spacing, axis, channel offset) live in `locate/calib/quest3s.json`, fitted with
  `python -m locate.real_eval calibrate <takes...>`. Use `real_eval --method tdoa` or
  `python -m separate --locate-method tdoa`. Default stays `level`.
  - **Leave-one-out on 6 takes:** 7°, 26°, 35° on clean front/side takes with strong head
    motion; 52–79° on "behind" and weaker takes (median 44°, 1/6 within 25°). A quicker
    prototype frame selection gave 14° / 17° / 23° on the same three, so expect ±10° from
    choices like that with this little data. Better than level, not yet reliable.
  - **Also overconfident:** the 79° miss reported "locked" at 0.80.
  - **Caveat:** the headset may apply some processing in hardware even on the UNPROCESSED
    mic source (the processed sources clearly do: mono, heavy noise suppression). Per-channel
    processing would blur exactly the sub-sample delays this mode relies on.
- **Since then (PRs #46, #50, #51; all simulated, nothing re-measured on a real 3S):**
  - **Tools.** `locate.bench` scores `level`, `tdoa`, and leave-one-out `tdoa-loo` / `phase-loo` /
    `adapt-loo` on the same labeled takes (median and p90 error by front / side / behind, front/back,
    seconds to lock, and whether the confidence is honest). Use `tdoa-loo` for any baseline: the stored
    calibration was fitted on 6 takes, so plain `tdoa` is graded on its own training data.
    `locate.diagnose` checks a take against what the delay model assumes (own fit, audio-vs-pose timing
    shift, clock span, channel coherence). `locate.pairsim` writes simulated 3S takes and two-talker
    scenes; `locate.scenes` and `locate.score_live --oracle` score locating each separated stream with
    the true stems standing in for the separation model.
  - **What limits the delay method on the real 3S is not yet known.** The real calibration leaves a
    delay residual of 13.7 us against a swing of only 14.6 us. In simulation, per-frame delay noise is
    about 1 us (known delay, even at 0 dB SNR) and a very reverberant room leaves about 2 us. So
    something the model leaves out dominates on the real headset: timing between audio and head pose,
    headset-side processing of the "UNPROCESSED" mics, or constants that change between takes.
    `locate.diagnose` on real takes decides this; it has not been run on any.
  - **A calibration depends on the rate it was fitted at.** In simulation the channel offset reads about
    5 us higher at 16 kHz than at 48 kHz, which put a talker 49 deg off on the live path. Calibration
    files now record `rate_hz` and `win`; the stored `quest3s.json` is a 48 kHz fit and the live hub
    (which measures at 16 kHz) warns about it. Refit with `real_eval calibrate --rate 16000`.
  - **Delay estimators.** GCC-PHAT stays the default. A phase-slope estimate with a per-frame error
    bar (`--delay phase`) and a per-source swing/offset model (`PairConfig.adapt`) are opt-in because
    neither beat it on 16 simulated takes (median 7.0 vs 8.5 deg but p90 23 vs 18.5) or 12 simulated
    two-talker scenes (median 8.5 vs 10.0 deg, both talkers within 25 deg in 10 vs 11 scenes).
  - **Confidence.** The posterior is blurred by 16 deg (`sys_sd_deg`) before confidence is read, so
    confidence can only go down and tops out near 0.8; the bearing still comes from the sharp peak.
    That does not stop a confidently wrong bearing (the 79 deg miss "locked" at 0.80), so "when it says
    90% it is right 90% of the time" is **not** shown. Settings that match the hit rate on the simulation
    (`pair.sim_tuned()`, less tempering and a looser ambiguity rule) are opt-in, because the simulation
    is underconfident while the real 3S was overconfident. Held-out simulated two-talker scenes: median
    10.5 deg, p90 27.0, front/back right 95.2%, both talkers within 25 deg in 8 of 12; default confidence
    ECE 0.44 (says 0.43, right 0.79), `sim_tuned` ECE 0.16 (says 0.69, right 0.79).
  - **The live default is still `level`** (`python -m separate --locate-method tdoa` opts in), and
    `level` fails on the real 3S. Switching the default needs real takes.
  - **Design only:** `hub/locate/FUSION.md` describes combining delay, level and head-motion history in
    one posterior and lists the real measurements that would justify building it.
- **Open:**
  - labeled real takes at every angle and distance, scored with `locate.bench` (the data plan is D16);
  - `locate.diagnose` on those takes, then fix what it points at;
  - a goodness-of-fit gate for the `locked` state and a per-device confidence floor, both needing real data;
  - camera bearings (SAM 3) for people in view are likely the more reliable route on the 3S;
  - audio channel order (left/right) is still unconfirmed on the headset;
  - the level estimator's male-voice bias and overconfidence (A8);
  - per-headset calibration needs a headset id in the protocol `Hello` (today it only says `quest3s`).

### D9. Vision: the SAM 3 image model per frame, not the SAM 3.1 tracker
**Proposed** (from A3 measurements, hardware-tested; C5 not built).
- **SAM 3 image model works on Windows** with the community `triton-windows` package. It runs
  with full-precision weights under bf16 autocast, as upstream does; converting the weights to
  bf16 breaks it.
- **The SAM 3.1 tracker needed three Windows workarounds,** then ran at ~15.5 s per frame and
  **crashed Windows twice** (bugcheck 0x00020001). Don't use it on this machine.
- **Prompt wording matters:** "child" scored 0.96, "person" only 0.27 on the same photo. C5
  should try several prompts or lower the threshold.
- **Expect ~2.5 frames per second.** Outlines will lag behind moving people.
- **Camera frames can now be recorded and replayed** (PR #44, replayed): `record_session.py` saves
  `video/<device_ts_us>.jpg` with a per-frame header in `video/frames.jsonl`, `mockclient.Session.load` and
  `mockclient.replay` read that layout, and a take can carry `talkers.csv` (who talks when, at what
  bearing) to score "box on the real talker". `hub/vision` holds only the model-free mask store so far.

### D10. Clean replay: replay MossFormer2's stream; SAM Audio is an optional cleaner
**Proposed** (from A3 measurements and a listening test; D3 task not built).
- **SAM Audio small-tv only fits if its core parts go on the GPU.** Those are the codec, the
  T5 text encoder and the DiT, ~4.4 GB peak.
- **Leave the unused parts on the CPU.** With text prompts and one candidate, the span
  predictor, the judge/CLAP rankers and the vision encoder aren't used.
- **Listening test:** text prompts ("a man speaking") removed the music from the voices, but
  **did not separate the two voices from each other.** MossFormer2 does. SAM Audio's SI-SDR
  was low (+1.9 / +5.4 / +2.5 dB), partly because the metric penalizes generative output.
- **Recommendation:** replay the last 5 s of the chosen MossFormer2 stream. Optionally run SAM
  Audio on that single-voice stream with a "speech" prompt to remove leftover noise (~2 s).
  Visual prompting (the speaker's SAM 3 outline) is the `-tv` model's strength, worth trying
  once camera frames flow.

### D11. Gemma stays off the M2 critical path
**Proposed.**
- **What decides M2:** separation, labels and locating. A language model can't separate audio
  or compute bearings.
- **Where Gemma fits:** describing the scene to the wearer from the hub's sources and the
  camera.
- **Memory:** only 4-bit E2B (2.9 GB) plausibly fits beside the live models.
- **Team decision already made:** run Gemma directly, not through the Gemini API
  (`.agents/decisions.md`).

### D12. Test without the headset: simulated sessions, a replayer, and scoring commands
**Merged** (PRs #15, #19, #23).
- **Simulator** (`mockclient.simulate`):
  - places mono sounds at world bearings and renders two ear-level mics on a turning head
    (Woodworth delay plus a 5-band spherical-head shadow);
  - writes 50 Hz head poses and per-source ground truth.
- **Replayer** (`mockclient.replay`): streams any session into the hub in real time over the
  real protocol.
- **Scoring:**
  - `separate.score` (SI-SDR improvement and labels) and `separate.suite` (11 scenes: 1-3
    voices, music, bird, turn-taking);
  - `locate.score_live` (bearing error vs truth);
  - `locate.real_eval` scores real 3S takes (PR #32);
  - `eval/` (PR #20) benchmarks streaming separators (ConvTasNet, SepFormer) on LibriSpeech
    mixtures, for the low-latency modes.
- **Demo audio:** `mockclient.demo_stems` makes reproducible demo clips.
- **Caveat:** the simulator assumes ear-level mics and no room echo. Real accuracy has to be
  measured on 3S recordings.

### D13. Model weights and recordings never go in git
**Merged.**
- **Weights:** downloaded at runtime to `hub/checkpoints/` (gitignored) or the Hugging Face
  cache. Sessions go in `hub/sessions/` (gitignored).
- **Gated models** (SAM 3, SAM Audio): each person requests access with their own Hugging Face
  account and logs in with their own token.
- **SAM Audio's first load is large:** ~28 GB of downloads, including companion models.
- **After a crash or interrupted download, verify the cache.** Corrupted files have kept their
  correct size.

### D14. Tracking: stable source ids from world bearing and label
**Merged and wired into the live hub** (PR #30 tracker, PR #37 events; simulated and replayed).
- `hub/track` turns the separator slots plus their world bearings into stable sources `t1`,
  `t2`, ... with a state (`tracking`, `last_seen`, `lost`) and an `in_view` flag. Input and
  output are protocol `Source` objects, so it slots in after `LiveLocator`.
- **Identity comes from world bearing plus label,** so a talker who pauses and returns in a
  different slot keeps their id (the case the separator leaves open, D7). Ids are never reused.
- `update()` must run on every tick (~10 Hz), even when nothing is heard; that's where
  `last_seen` and `lost` happen.
- **Now:** `hub/events` owns the Tracker, calls `update()` every 100 ms and publishes `/tracks` and
  `/events`; the headset's choice is a tracker id (D15). Bearing smoothing is a time constant now
  (`smooth_tau_s` 0.6 s, `follow_tau_s` 0.3 s, PR #50) instead of a per-tick gain. Simulated, on the
  live locator's output: tick-to-tick step p95 0.32 -> 0.20 deg, but a 20 deg jump takes 0.85 s instead
  of 0.45 s to cover 80%. `python -m track.jitter` measures that. It inherits D8's accuracy: a 30–45°
  male-voice bias can split one person into two tracks.

### D15. The chosen voice goes back on `/audio/out`: inner = the voice, outer = the room
**Merged** (PR #42, M2; replayed and mocked, **not yet heard on a headset**). Details in
[`hub/out/README.md`](hub/out/README.md).
- **Choice = a tracker id.** The headset's select / stop / next / prev arrive as `InputEvent` on
  `/ingest/pose`; selecting by ray picks the non-lost source nearest the ray within 30 deg. Per audio
  frame the Tracker says which separator slot carries the chosen id, so a slot swap or a pause does not
  change who you hear. Voice memory (D7) only helps the two voice slots stay consistent.
- **Wire format** matches `AudioOutPlayer.cs`: 960 frames, 48 kHz, 2 channels, s16le, every 20 ms.
  `layers` (what the Quest uses): channel 0 inner, channel 1 outer, `target_bearing_deg` for the 3D
  position. `stereo` is for simple clients.
- **Volumes are applied on the headset** for `layers`, so the hub only stores them; applying them
  twice would double the change.
- **Delay:** audio waits 0.3 s so the Tracker has seen the same hop, plus 0.2 s of jitter margin after
  idle; the queue is bounded at 1.8 s. This comes on top of D7's 1–2 s.
- **Measuring the margin (PR #43, simulated):** `python -m separate.measure_chosen` reports how many dB
  louder the chosen voice is than the others, and how soon after selecting. It needs ground-truth stems,
  so it refuses real recordings.

### D16. Real-data plan: labeled takes, a data check, a round-trip delay test, alerts rules
**Merged** (PR #49; synthetic and mocked only: nothing was run on a Quest or on real recordings).
- **Takes.** `run_locate_take.ps1` records pink noise or speech at a known angle, now labeled with
  distance, head-movement size (small / normal / large) and stimulus, plus `audio_chunks.csv` with every
  chunk's device timestamp. The grid to fill is 12 angles (every 30 deg) x 0.5 / 1 / 2 m.
- **Data check** (`eval/dataset_check.py`): a take passes if the source is at least 6 dB over the room,
  the head turned enough, the angle is labeled and the clocks look sane (pose gaps, audio-vs-pose span,
  chunk timestamps measured against their median offset so one noisy chunk does not fail a take,
  recorder restarts). A grid cell counts only with a passing take; exit 0 needs a full grid and 90%
  passing. Takes recorded before the labels existed show up in an "unlabeled" column and are warned about,
  not failed. The tolerances are guesses until real takes exist.
- **Round-trip delay** (`eval/delay_test.py`): a chirp is sent on `/audio/out`, played by the headset,
  heard by its mic and timed when it returns on the mic stream, so no clock sync or app change is
  needed. At least 30 trials, median / p90 / worst. The pass budget (150 ms median, 300 ms worst) is an
  assumption. A mic-to-hub-to-headset echo would need a hub change that does not exist. Only the mock
  mode has been run.
- **Alerts** (`eval/alerts_rules.json`, `eval/alerts_check.py`): smoke alarm, siren and the wearer's name,
  checked offline. The live pipeline only carries coarse labels, so a smoke alarm can fire only as a
  non-critical "alarm sound" until the fine AudioSet classes are exposed; the name rule needs speech
  recognition the repo does not have.
- **Results** (`eval/results_table.py`): one table from `locate.bench --json` and the delay JSON against
  the location targets.

### D17. Autonomous audio-visual sound discovery: specified, phase 1 only (no models)
**Merged** (PRs #45 spec, #48 phase 1; deterministic code and fixtures only). The spec
([`docs/AV_SOUND_DISCOVERY_SPEC.md`](docs/AV_SOUND_DISCOVERY_SPEC.md)) turns a recorded scene into
persistent sound sources: events, acoustic sources, visual tracks and time-bounded associations kept
distinct, with bounded refinement. Phase 1 ships contracts, a cache, spatial pair-delay and aliasing
checks (`hub/locate/av_spatial.py`), residual math, envelopes, the matcher and a viewer bundle
(`hub/av_scene`, `hub/who`, `hub/replay`, `hub/render`, `hub/vision`, `eval/av_scene`), run with
`python -m av_scene preflight | inspect | serve | fixture`. It needs no weights or GPU and is not in the
live path; the model phases (SAM 3 masks, SAM Audio stems) are not built. It does not change the live
defaults.
